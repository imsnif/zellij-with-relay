# Hosted Relay Deployment Action Plan

## Goal

Replace the existing development relay on the current VPS with the Stage 2
hosted relay while retaining both browser viewing and native Zellij access.

This is a development deployment. Only test users and test data are allowed.
It is not the final production deployment or final public-domain layout.

## Open-source and self-hosting requirement

All code added on this branch is intended to remain public and open source.
Hosted `zellij.online` operation is one deployment of the relay, not a special
code path that independent operators must depend on.

The implementation must preserve these properties:

- standalone self-hosting remains supported and remains the default relay
  authentication mode;
- hosted mode can target any compatible HTTPS control plane, not only the
  zellij.online website;
- app origin, relay origin, public URL, allowed browser origins, TLS hostname,
  and control-plane URL are operator configuration;
- no secret, account identifier, Cloudflare project name, Workers URL, VPS
  address, or private deployment detail is committed as a required default;
- Cloudflare Pages is a reference deployment target, not a runtime dependency.

The official service is the product being launched and may receive the best
defaults, automation, documentation, and domain conventions. Self-hosting only
needs to remain technically possible through documented configuration; it does
not need to be zero-configuration, support every arbitrary topology, or match
the operational convenience of zellij.online.

Branded values such as `zellij.online` may remain as defaults, examples, and
additional official-service security hardening. They must not make the relay
binary depend on the hosted website or prevent an operator from running
standalone mode with their own app/relay domains. Requiring self-hosters to use
the documented paired-domain convention (`app.example` and
`relay.app.example`) is acceptable for now.

## Phase 3: Make the app origin target an explicit relay

The current app-origin build derives the relay by prepending `relay.` to the
app-origin hostname. That would incorrectly turn a Pages hostname into
`relay.<viewer-project>.pages.dev`.

Add an explicit relay-origin build option, for example:

```sh
cargo x build \
  --app-origin out/ \
  --app-host <viewer-project>.pages.dev \
  --relay-origin https://relay.zellij.online
```

**Implemented locally (pending review/commit):** `--relay-origin` accepts a
validated HTTP/WebSocket origin, normalizes it into paired HTTP and WebSocket
origins, and emits a trusted runtime `<meta>` plus CSP and `_headers` values
from that single configuration. Secure HTTPS/WSS is required remotely;
insecure HTTP/WS remains limited to loopback development. Omitting the option
retains `relay.<app-host>` derivation. The artifact now also generates the
Pages-compatible `_redirects` and `_headers` files. They are intentionally
excluded from `RELEASE_HASHES.txt` because Pages consumes rather than serves
them; deployed routing and response headers must be verified separately.
Generic static hosts may ignore those files and configure equivalent
routing/headers themselves.

The selected relay origin must drive all of the following:

- browser HTTP requests to the relay;
- browser WebSocket connections;
- generated CSP `connect-src` values;
- runtime relay-target validation;
- local-development and app-origin tests.

Requirements:

- Default behavior for the final paired-domain layout may remain
  `<app-host> -> relay.<app-host>`.
- An explicit relay origin must override derivation.
- The option and generated runtime metadata must be generically named; do not
  add a zellij.online-specific or Cloudflare-specific branch.
- Only `https://`/`wss://` remote targets are permitted; loopback development
  may continue to allow HTTP/WebSocket exceptions.
- The relay target must not be accepted from an untrusted share-link query or
  fragment parameter.
- Add tests covering an autogenerated `pages.dev` app origin connected to
  `relay.zellij.online`.
- Generate CSP and browser runtime targeting from the same parsed relay-origin
  configuration so the two cannot drift.

### Future custom-domain simplification (not available for this deployment)

`zellij.online` cannot host the app origin yet. This development deployment
must therefore use the temporary autogenerated `pages.dev` URL and implement
the explicit relay-origin support above.

In a later deployment, assigning `zellij.online` to the app-origin project
would match the upstream convention exactly:

```text
zellij.online        -> app origin
relay.zellij.online  -> relay VPS
```

That future layout would avoid both the explicit relay-origin override and the
native attachment workaround in Phase 5. It is not an option for the current
development deployment and must not block the temporary Pages work.

## Phase 5: Resolve native attachment for the temporary Pages URL

The native attach parser currently transforms:

```text
https://<app-host>/r/<slug>
  -> https://relay.<app-host>/r/<slug>
```

Therefore, a native client given the temporary Pages share URL would derive a
nonexistent `relay.<viewer-project>.pages.dev` hostname.

For the initial development deployment, use two equivalent forms of the link:

- browsers use
  `https://<viewer-project>.pages.dev/r/<slug>#k=<secret>`;
- native clients use
  `https://relay.zellij.online/r/<slug>#k=<secret>`.

To attach natively, manually replace only the Pages hostname with
`relay.zellij.online`. Preserve the slug, `#k` secret, and any other fragment
parameters exactly. This needs no additional URL protocol or client work and is
the selected workaround for the first deployment.

Self-hosters can continue to use either direct relay URLs or the existing
paired-domain convention. Phase 11 records the follow-up client change that
will remove the temporary two-link behavior for unrelated app and relay
origins.

Read-only and full-control native attachment were verified on 2026-08-12 using
the direct-relay URL workaround. Two native-client usability issues were found:

- remote attachment has no local-only detach key; read-only mode suppresses all
  stdin, so there is no keyboard path out of the attached client;
- in full-control mode, `Ctrl+D` is forwarded to the shared terminal as EOF. If
  that exits the final shell, it closes the shared session rather than merely
  detaching the viewer.

Until a local detach mechanism exists, close or terminate the local attach
client without sending `Ctrl+D`. Follow-up client work should add a local
escape/detach sequence that is handled before read-only input suppression or
full-control input forwarding, closes both viewer connections, and restores the
local terminal without sending the escape bytes to the shared session.

## Phase 10: Stabilize or use a temporary fallback

The goal is to stabilize the new separated architecture. Temporary relay
downtime during development is acceptable, and failure of one acceptance test
does not require restoring the obsolete embedded-viewer deployment.

If hosted integration fails but the new relay is otherwise sound, redeploy the
new stack in standalone mode using the preserved relay-data volume while the
control-plane issue is fixed.

If the new protocol, transport, or viewer is broken, diagnose and fix forward.
The recorded old image ID is only a last-resort diagnostic fallback; restoring
the current embedded browser viewer is not a deployment requirement. Never use

## Phase 11: Add explicit relay origins to native share-link handling

After the initial hosted deployment works with the Phase 5 workaround, extend
the share-link format and native client so one generated URL works for both the
Pages viewer and native Zellij attachment. A candidate format is:

```text
https://<viewer-project>.pages.dev/r/<slug>#k=<secret>&relay=https%3A%2F%2Frelay.zellij.online
```

Implementation requirements:

- link generation includes the configured public relay origin;
- the native client reads and validates the explicit relay origin before
  falling back to the existing `relay.<app-host>` derivation;
- remote relay origins require HTTPS/WSS, while HTTP/WS remains restricted to
  loopback development;
- credentials, paths, queries, fragments, malformed hosts, and ambiguous ports
  in the relay-origin value are rejected;
- the browser continues to use only its trusted build-generated relay target
  and must not allow the share-link parameter to override CSP or runtime relay
  selection;
- the key and relay metadata remain in the URL fragment so the app-origin host
  does not receive them in HTTP requests;
- direct relay URLs and existing paired-domain links remain compatible;
- tests cover explicit unrelated domains, legacy fallback behavior, malformed
  inputs, downgrade rejection, and preservation of `#k` plus other fragment
  parameters.

The relay origin is routing metadata rather than a secret. The attachment key
remains the sensitive value. This change should stay generic and configurable;
do not hardcode the Pages project or `zellij.online` into native resolution.
